# Android App (Capacitor) — Phase 2

## What it is

A native Android shell around the same Vite web app (`android/`,
generated by Capacitor 8, app id `com.amardokan.pos`, app name
"Amar Dokan POS"). The web app is bundled into the APK/AAB from `dist`
— there is no separate Android codebase to keep in sync. The server
(and its API) is unchanged: the app talks to the same backend over
HTTPS.

## Build locally (needs Android SDK + JDK 17 — not present in the sandbox)

```sh
bun install
npm run cap:sync        # CAPACITOR_BUILD=true build (no service worker) + cap sync
cd android && ./gradlew assembleDebug   # unsigned debug APK for on-device testing
```

## Caching strategy — no service-worker double-caching

This is the rule the whole shell is built around:

- **Web/PWA build** (`npm run build`): registers the Workbox service
  worker as before.
- **Capacitor build** (`CAPACITOR_BUILD=true npm run build`, used by
  `npm run cap:sync` and the Android workflow): `vite.config.ts`
  omits the VitePWA plugin entirely, so `dist` contains **no** `sw.js`
  and no service-worker registration code.
- **Offline-first in the native shell** therefore comes from exactly
  one mechanism: **AmarSync** (`services/amarSync.ts`) — the
  localStorage outbox + cached products, flushed to the server on
  reconnect, with the server-side sale-id conflict check making a
  retried flush idempotent (no duplicate stock deduction). The WebView
  does not cache API responses itself.

If you ever see a service worker inside the native app, the
`CAPACITOR_BUILD` gate has been broken — fix `vite.config.ts`, do not
work around it in the app.

## Native sync indicator

The app shell's sync pill (top bar, `data-testid="sync-indicator"`)
is the native sync indicator: it shows the live AmarSync pending count
(`🔄 N Unsynced`), `Syncing…`, `Offline`, or `✓ Synced`, and opens the
sync reconciliation modal. Inside the native app an additional
`📱 App` badge (`data-testid="native-badge"`) confirms the shell is
native rather than a browser tab. The pill is driven by the same
`subscribeSync` feed on web and native — one indicator, not two
competing ones.

## Bluetooth thermal printing

- The receipt text is the **same ESC/POS text** the web app already
  generates (`components/Invoice.tsx`), including the paper-cut
  command. Nothing about the receipt format changed.
- In the Android app, the Invoice shows a **Bluetooth Print** button
  that uses `@capacitor-community/bluetooth-le`:
  initialise → pick a printer → connect → discover services → write
  the ESC/POS bytes to the first writable characteristic. Printers
  differ in UUIDs, so discovery is generic (first characteristic with
  `write` / `writeWithoutResponse` wins).
- On the web, or whenever Bluetooth fails, the button is absent /
  reports the failure and the **ESC/POS .txt download stays the
  fallback** — it was not removed or changed.

### On-device printing checklist (UNVERIFIED — must be run by the owner)

No phone or Bluetooth printer exists in the sandbox, so this path is
code + build verified only. Before calling printing "working":

1. Install a debug APK from `npm run cap:sync` + `assembleDebug` on a
   real Android phone; pair the phone with the thermal printer in
   Android Settings first (BLE printers vary — some need pairing, some
   advertise openly).
2. Open a sale, open its Invoice, tap **Bluetooth Print**, pick the
   printer, and confirm a receipt prints with correct totals and the
   ৳ amounts readable. If ৳ prints garbled, that printer needs a
   code-page setting — note the printer model and treat it as a
   per-printer configuration issue, not a silent success.
3. Confirm the failure path: with Bluetooth off, tapping the button
   reports the failure and the ESC/POS .txt download still works.
4. Only after steps 2–3 pass may printing be described as verified,
   and only for the tested printer model.

## Signed release builds (GitHub Actions)

`.github/workflows/android.yml` builds a **signed APK + AAB** whenever
a `v*` tag is pushed to main, and attaches both to the tag's GitHub
release. It fails closed when signing secrets are missing — it never
signs with a debug key.

### Keystore setup checklist (owner, one time)

The keystore and its passwords live **only in GitHub Secrets** — never
in the repo, never in `.env`, never in chat:

1. On a machine you trust (not a shared server), create the upload
   keystore once:
   `keytool -genkeypair -v -keystore amar-dokan-release.keystore -alias amar-dokan -keyalg RSA -keysize 2048 -validity 10000`
   Guard the passwords: losing the keystore means a new app listing
   for updates (Android requires the same key for updates).
2. Base64 it: `base64 -w0 amar-dokan-release.keystore` and store the
   output as the `ANDROID_KEYSTORE_BASE64` secret.
3. Add the other three secrets with the exact passwords/alias from
   step 1: `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`,
   `ANDROID_KEY_PASSWORD`.
4. Push a tag (`git tag v1.0.0 && git push origin v1.0.0`) and watch
   the Android Release workflow. A green run attaches the APK + AAB
   to the release; a red run at the secrets check means a secret is
   missing or misnamed — fix the secret, re-run, do not commit a
   keystore to "make it pass".
5. Back up the keystore file itself somewhere encrypted and offline.
   GitHub Secrets are not a backup of the keystore file.

### What is NOT proven here (honest limits)

- **No signed APK/AAB was produced in this environment**: no keystore
  or signing secrets exist here, and no Java/Android SDK is installed.
  The deliverable is the workflow + the signing wiring + the
  Capacitor build proof (`cap sync` + web build). The first signed
  artifact must come from the workflow run in step 4 above.
- **Bluetooth printing is UNVERIFIED on a real device** (see checklist).
- **No Play Store listing exists** from this work; the AAB is the
  upload artifact for a listing the owner creates separately.
